Start with your wedding. Keep the extra platform work out.

One configured wedding, one dedicated deployment, and accounts you can access yourself.

Included in the target

Guest and organizer access, event invitations, dependable replies, practical weekend information, and curated guest styling.

Not needed for one wedding

Public couple signup, subscriptions, billing, a marketplace, or a control panel for many wedding sites. There is no separate CMS to manage.

Still necessary

Guest privacy, explicit permission to reply for another person, backups, account recovery, and someone responsible when things go wrong.

Build and verify it in this order.

An agent can guide the technical work. You retain control of the accounts, spending, real guest information, and launch decision.

No paid plan or running-cost estimate has been approved. Check current plans and limits before creating resources.

  1. Run the fictional prototype

    Clone the repo and follow the README. No cloud accounts are needed for local review.

  2. Build one complete RSVP path

    Use local SvelteKit and Supabase. Prove that a guest’s saved answer survives reopening and appears correctly for the organizer.

  3. Set up a hosted rehearsal

    After choosing accounts and budget, create the app and database, configure sign-in mail, and connect deployment to GitHub. Keep the data fictional.

  4. Finish the agreed wedding controls

    Add event and people editing, reply permissions, content, and styling. Review the rules for changing events after guests are invited.

  5. Rehearse recovery, then decide on launch

    Test unauthorized access, corrections, uncertain saves, phone use, and restoring records and images. Import real guests only after a separate launch decision.
